# Публикация и дальнейшие обновления

## Репозиторий

Публичный репозиторий исходного прототипа: https://github.com/yolatherola/1c-designer-mcp. Основная ветка — `main`.

Разрешение владельца от 22.10.2026 относится к публикации выделенного технического пакета и документации. Репозиторий использующего проекта, его Git-история, прикладные BSL/XML, подключения, captures, runtime-state и сторонние бинарники в публикацию не входят.

Это публикация исходного снимка, не выпуск проверенного самостоятельного сервера. `source_publication_approved=true` фиксирует разрешение на этот состав; `standalone_runtime_verified=false` и `public_release_approved=false` сохраняют отдельный статус готового runtime-релиза. Поля исходного `SOURCE_MANIFEST.json` описывают момент выделения снимка и не являются текущим статусом публикации.

## Обновить README или документацию

Из отдельного checkout этого репозитория:

```sh
git pull --ff-only
git switch -c codex/update-readme
# Изменить нужные файлы.
python -B scripts/check.py
python -B scripts/review_publication.py
python -B -m unittest discover -s scripts -p "test_*.py"
git diff --check
git diff
git add README.md
git diff --cached
git commit -m "docs: update README"
git push -u origin codex/update-readme
```

Добавляйте в индекс только фактически изменённые файлы задачи; для других документов замените `README.md` точными путями. Затем создайте pull request в `main`, дождитесь CI и проверьте итоговый diff. Не используйте force-push для обновления основной ветки.

## Обновить исходники

До независимой приёмки действующий backend разрабатывается в исходном использующем проекте. Переносите только проверенную техническую правку по явному списку; не копируйте весь проект, его историю или состояние сеанса. Сначала проверьте изменения исходного дерева, зависимости, права на сторонние фрагменты и публичный состав.

`SOURCE_MANIFEST.json` сохраняет SHA первоначального снимка. Для изменённых существующих файлов проверка без `--verify-origin` допускает новый текст; для добавления/удаления файлов обязательно обновите состав манифеста. В PR укажите изменённые пути, происхождение и фактические проверки новой версии. Старый unit PASS не подтверждает новую правку и не заменяет испытание живого backend.

Из отдельного checkout запускайте все три автономные команды выше. Публикуйте точный коммит с результатами CI. Дата, hash и ограничения проверки должны относиться к этой версии.

## До самостоятельного runtime-релиза

1. Локальный профиль вместо фиксированных root/fixture UUID и исторических квитанций.
2. Явный каталог состояния, свежий bootstrap и документированные внешние SDK/зависимости.
3. Воспроизводимая сборка native-компонента без сторонних бинарников в исходном пакете.
4. Один принятый сценарий на чистом checkout: чтение → точная правка собственной безопасной fixture → независимое чтение результата → завершение ресурсов.
5. Лицензия собственного кода и проверка происхождения сторонних фрагментов.
6. После приёмки — подключение использующего проекта к единственной канонической версии вместо двух рабочих копий.

`review_publication.py` проверяет состав и несколько известных сигнатур. Содержательное ревью новых файлов и данных остаётся обязательным. Лицензия ещё не выбрана; лицензированный публичный релиз пока не объявлен.
